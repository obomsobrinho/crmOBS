# Deleting a company in two steps: Desativar (reversible) and Apagar de vez (one routine, export first)
- Date: 2026-10-15
- Status: Accepted (owner decisions of 14/10/2026 in `docs/plano-central-clientes.md`, section 5; revised by the owner on 15/10/2026: billing history kept, Evolution instance deleted, see "Revision")
- Area: admin, data, security

## Context
The owner needs to remove a company that stops using the CRM, and LGPD gives the company the right to its data and to deletion. A company's data is spread over 18 tables with `client_id`, two Storage buckets, an Evolution instance, an Asaas subscription and its logins. Deleting by hand forgets something; deleting by mistake cannot be undone.

## Decision
- Two steps, both in the central's tab "Ações" (a separate tab, "zona de perigo"), both server routes guarded by `rotaDoAdmin(..., { revalidar: true })`, both written in `admin_acoes`.
- DESATIVAR / REATIVAR (`PUT /api/admin/empresas/[id]/conta`, actions `desativar`/`reativar`, `clients.desativada_em`): nothing is deleted. Enforced on the server, never by hiding UI:
  1. `getMyClient` exposes `contaDesativada` (deactivated AND the login is not in `ADMIN_USER_IDS`: the product owner is never locked out of his own central);
  2. pages: `barrarContaDesativada` in `app/(app)/layout.tsx`, `requireActiveTenant`, `/montagem`, `/assinatura`, `/connect` and the landing send to `/conta-desativada`, a clear screen (company name, nothing was deleted, "Sair"), never an error; a spec fails when a page outside `app/(app)` reads the session without the check;
  3. routes: `sessaoDaRota` answers 403 `conta desativada` to every session route, reads included (send, orientar, resolve, agent config, team, knowledge, photos, playground); `/api/fotos` read the session by hand and was moved to `sessaoDaRota` in review, and a spec now fails when a route imports `getMyClient` or the session client without the guard;
  4. the AI: `processTurn` returns the silent turn (`diagnostics.contaDesativada`, `silenced = desativada`) before everything, bench included; n8n keeps recording incoming messages, so nothing is lost.
  Known gap, listed for the owner: a tab that was already open keeps its Supabase session, so RLS still answers direct PostgREST reads and the granted column writes until it navigates. Closing that needs the deactivation in the tenant RLS helper (a production-wide policy change, not done here).
- APAGAR DE VEZ (`POST /api/admin/empresas/[id]/apagar`, body `{ nome }`): only for a DEACTIVATED company, confirmed by typing its name (trimmed, exact, checked in the route and again in SQL under the row lock). Before it the tab offers the LGPD export: `GET /api/admin/empresas/[id]/exportar`, a ZIP with ONE CSV PER TABLE (owner decision) plus `cliente.csv` and `membros.csv`, streamed (`lib/zip.ts`, deflate per chunk, no library; the CRC table stays hand-written because no `engines`/Node pin guarantees `zlib.crc32`, Node >= 20.15, and Next 16 only requires >= 20.9) and read in batches (`admin_exportar_lote`, `LEITURA_DA_EXPORTACAO`): big tables keyset by an EXISTING `(client_id, created_at|opened_at)` index plus `id` (Index Scan Backward plus Incremental Sort, no new index on `chat_messages`, which would lock writes), a second pass for rows whose ordering column is null, the others by primary key; 2000 rows per batch, 200 for `knowledge_chunks` (vectors). Measured on 15/10/2026 on a synthetic temp copy: 200,000 messages in 101 batches took 5.5 s in the database (network not included), well inside the route's `maxDuration` of 300 s. Memory is bounded; the export itself writes an `admin_acoes` row. Storage files are not in the ZIP (their paths are, in the rows).
- ONE routine, `apagarCliente` (`lib/admin.ts`), in an order that can be retried without losing anything:
  1. checks (exists, deactivated, name) and `admin_tabelas_fora_da_purga` over `TABELAS_DO_CLIENTE` plus `TABELAS_MANTIDAS`: a table with `client_id` missing from both lists stops everything BEFORE any external effect;
  2. reads the logins that belong to no other company (`admin_usuarios_so_do_cliente`), never an `ADMIN_USER_IDS` id;
  3. cancels the Asaas subscription with the existing `deleteSubscription` (a 404 means already gone; any other failure stops, nothing deleted; another provider has no integration and becomes a pending item);
  4. removes the company's Storage files (every path starts with `{client_id}/`; listed by `admin_arquivos_do_cliente` per bucket by a range on the `name collate "C"` index, in batches of 1000, removed through the Storage API, stopping if a batch does not move or comes back incomplete);
  5. logs the WhatsApp out (`logoutInstance`) and DELETES the Evolution instance (`deleteInstance`, `DELETE /instance/delete/{instance}`; 404 means already gone). A failure does not stop the routine: it becomes a pending item to delete it in the Evolution panel (revision of 15/10/2026; before it there was no delete helper and the instance stayed);
  6. `admin_apagar_cliente`: one transaction, row locked, checks again, verifies the catalog against the list again (calling the same `admin_tabelas_fora_da_purga`), stamps the KEPT tables (`p_mantidas`: `deleted_client_id`, `deleted_client_name`), deletes every listed table children first, deletes the `clients` row (the kept rows get `client_id` null through their `on delete set null` key), and writes the `admin_acoes` row (who, when, name, id, created and deactivated dates, row counts per table; no content). `admin_acoes` has no `client_id`, so the record survives;
  7. deletes the logins from step 2 with `auth.admin.deleteUser`; a failure is a pending item.
  The response is `{ ok, pendencias }`; the screen shows the pending items to resolve by hand. From step 3 on, every stop or error (Storage failure, the purge RPC failing or answering non-ok) goes through one exit that adds what was ALREADY done outside the database ("A assinatura já foi cancelada no Asaas.", "N arquivos já foram removidos do Storage.", the WhatsApp logout or the deleted instance; `pendenciasDosEfeitos`, `lib/admin-conta.ts`) and logs it with the client id; a database error there answers `falha_banco` (500) with those items, never a silent 500 (code review of 15/10/2026).
- The table list is `TABELAS_DO_CLIENTE` (`lib/admin-purga.ts`), in delete order (`conversations` before `pipeline_stages`, `knowledge_chunks` before `knowledge_documents`: those keys have no cascade). Three guards so a new table is never forgotten silently: the SQL catalog check (twice, before the external effects and inside the transaction), `e2e/central-clientes-conta.design.spec.ts` comparing the list with every table that has `client_id` in `lib/database.types.ts` (regenerated with each migration), and `e2e/central-clientes-conta.serial.spec.ts` deleting a disposable company and counting zero rows in every listed table.

## Consequences
- A new table with `client_id` must enter `TABELAS_DO_CLIENTE` (in the right order) or, when it must survive the purge, `TABELAS_MANTIDAS`, in the same delivery, or the sem-login spec fails and, in production, "Apagar de vez" refuses to run.
- `billing_events` rows of the company SURVIVE the purge (fiscal record, owner decision of 15/10/2026) and still go into the export. After the purge they have `client_id` null and `deleted_client_id`/`deleted_client_name` filled; the `admin_acoes` row of the purge has the same id.
- The ZIP has no ZIP64: a single CSV over 4 GB, or more than 65,535 files, fails with a clear error.
- Tests never purge a real tenant: the serial spec creates its own company (`provision_tenant`, a dedicated login, DDD 00 data, one Storage file), purges it and checks; its `afterAll` cleans up if anything fails midway. OBS is only deactivated and reactivated, restored in `afterAll`.
- Evidence: rolled-back SQL run on 15/10/2026 (refused while active, refused with another name, purge of a seeded disposable company left 0 rows and the audit row); the specs above.

## Revision 15/10/2026 (owner)
- Billing history is kept. `billing_events` left `TABELAS_DO_CLIENTE` and is the only entry of `TABELAS_MANTIDAS` (`lib/admin-purga.ts`); the export reads `TABELAS_DA_EXPORTACAO` (both lists). Its key to `clients` was already `on delete set null` (migration 20260814033651), so it neither cascades nor blocks; the minimal change was two nullable columns, `deleted_client_id` and `deleted_client_name`, so a row stays readable without the `clients` row. `admin_apagar_cliente` gained `p_mantidas text[] default '{}'` (migration 20261015191433, the five-parameter version dropped; the deployed code calls it with five named arguments and keeps its old behavior until the deploy): the catalog check runs over both lists, so a NEW table with `client_id` in neither still aborts; a table in both lists aborts; a kept table must have no key to `clients` other than `on delete set null` and must have the two columns, which the function fills before deleting the company. The purge audit row records the kept counts (`depois.mantidas`). Proven in a rolled-back transaction on 15/10/2026: the old five-argument call still deleted the row, the new call kept it with `client_id` null and the id and name filled, the missing list and the overlap both raised.
- The Evolution instance is deleted: `deleteInstance` (`lib/evolution.ts`) calls `DELETE /instance/delete/{instance}` with the global `apikey`, confirmed on 15/10/2026 in the Evolution API v2 reference and in the project source (Context7: `/websites/doc_evolution-api_v2_api-reference`, `/evolution-foundation/evolution-api`, route table `DELETE /instance/delete/:instanceName`; 200 `{ status: "SUCCESS" }`, 404 when the instance does not exist). The deployed Evolution is 2.3.x (comment in `lib/evolution.ts`). Per the docs the delete also logs out an open or connecting instance; the routine still calls `logoutInstance` first, and only when the delete fails do the logout failure and "apague no painel da Evolution" become pending items.
