# Client information added to an open help request updates that request
- Date: 2026-10-08 (target chosen by the model since 2026-10-13)
- Status: Accepted
- Area: agent, data, pedidos

## Context
A help request kept the summary of the turn that opened it. When the client added information while it waited (request "quer saber o prazo de entrega", later "preciso até sexta"), the team saw a stale request in Pedidos, in the conversation composer and nowhere else. The owner asked for the request to be UPDATED.

How a turn with an open request worked before this change (`lib/agent-turn.ts`): the model sees `### PEDIDOS DE AJUDA EM ABERTO` and answers `pedido_novo`; a request enters the queue only when there is none open, or when it is new and the code safety net `mesmoAssunto` agrees (no shared subject word means new). A turn about an already-open request opened nothing and changed nothing. With `action = none` the schema asks for an empty summary, so a client merely adding a detail produced no usable summary at all.

The first version (2026-10-08) let the CODE pick the target by subject-word overlap and treated any differing summary as new information. The attendance battery showed the flaw: case M10 ("valeu, obrigado" on an open price request) rewrote the summary in 1 of 5 runs, because a thank-you turn answered `pausar` with a reworded summary. Word overlap cannot tell new information from a reworded repeat, and it guessed the target.

## Decision
- The MODEL says which request and whether it is new information, in two fields of the strict output schema (`lib/agent.ts`, descriptions in the schema like `motivo`): `pedido_aberto` (integer, the request's number in the `### PEDIDOS DE AJUDA EM ABERTO` list, 0 = none) and `informacao_nova` (boolean; insisting, chasing, thanking, confirming or repeating is false). `normalizeOutput` keeps only a positive integer; the guardrail's degraded output and the silenced turn send 0 and false.
- The rule is pure and only VALIDATES: `atualizacaoDoPedido` in `lib/fila-de-pedidos.ts` updates only when ALL hold: not the `retomada` turn; `action = pausar`; the guardrail did not block; the turn did NOT enter the queue; `informacao_nova` is true; `pedido_aberto` points to a request in the list; the summary is non empty and differs from the stored one (case, accents and spacing ignored, with `normalizar` from `lib/clientes.ts`). No scoring, no tie handling, no guess. `mesmoAssunto` stays only as the queue safety net.
- Queue decision, pure and tested: `entraNaFila` (`lib/fila-de-pedidos.ts`). When the model points to a listed request (`pedido_aberto` valid in the list), says `informacao_nova` and `pedido_novo = false`, the turn is an UPDATE of that request and the `mesmoAssunto` net does not apply (code review 2026-10-13: a rewritten summary such as "Precisa até sexta" shares no subject word with "prazo de entrega" and would have become a NEW request with a WhatsApp notice). In every other case the net is exactly as before.
- The numbered list the model sees and the list the decision indexes are the same array (`listaDoModelo` in `processTurn`: open requests oldest first, empty summaries left out), so a number always means the same request.
- `processTurn` writes, server side and best-effort, in parallel with the qualification insert: `summary`, `atualizado_em = now()` and `motivo` only when the request had none, filtered by `id`, `client_id`, `phone` and `closed_at is null` (a closed request never changes). It NEVER sends a WhatsApp notice: only a new request notifies. `dryRun` writes nothing and reports `diagnostics.pedidoAtualizado`, shown in the bench summary panel.
- Prompt: one sentence in the `### PEDIDOS DE AJUDA EM ABERTO` block (`pedidosAbertosBlock`), present only when a request is open: when the client adds something to a listed request, answer `pausar`, `pedido_novo = false`, its number in `pedido_aberto`, `informacao_nova = true` and the full request with the new information in `summary`. This is prompt text for every tenant (not the persona, so `LIMITS.persona` is unaffected) and needs `test:e2e:ia` and the attendance battery before deploy.
- Data: `handoffs.atualizado_em timestamptz null` (migration `20261009005834_pedido_atualizado.sql`), returned by `pedidos_pagina`. Pedidos shows "atualizado às HH:MM" (or "em" with the day) under "Aberto em" in the facts strip. Realtime needs nothing new: the `handoffs` UPDATE event already makes Pedidos refetch that conversation's open queue and the selected request, and the conversation's `useHandoffsDaConversa` patches the row from the payload.

## Consequences
- The first open request's `opened_at` (and `conversations.handoff_at`, the wait) does not change on an update: the wait still counts from the opening.
- If the model answers `none`, or `informacao_nova = false`, nothing is updated; the schema and the prompt sentence are what make the update happen, so their effect is measured by the paid suites (bateria M9 must update, M10 must not).
- Two more required output fields for every turn (strict schema): n8n ignores them.
- Proof: `e2e/pedidos.design.spec.ts` ("Pedido em aberto atualizado pelo cliente": update and motivo fill, target by number in list order, every no-update condition, the queue exception with no shared word, `mesmoAssunto` unchanged; the facts strip line on `/design/pedidos`); `e2e/bateria/casos-obm.ts` M9 and M10 (real brain).
