# Vitalício in the access rule and manual block (the beta switch removed)
- Date: 2026-10-15
- Status: Accepted (owner decisions of 14/10/2026 in `docs/plano-central-clientes.md`, section 4; revised by the owner on 15/10/2026: the beta switch is removed, see "Revision"). Supersedes `docs/adr/2026-09-23-beta-open-master-switch.md`.
- Area: billing, admin, data

## Context
`BETA_ABERTO=1` (`docs/adr/2026-09-23-beta-open-master-switch.md`) frees every tenant. Turning it off would lock every beta signup whose 7-day trial already ended, and the owner wants some companies free forever ("um formato vitalício que nunca cobra"). `account_type` cannot do it: it identifies and never authorizes (`docs/adr/2026-08-28-account-type-identifies-not-authorizes.md`). A code review of delivery 1 also found that `situacaoDaConta`, the alerts and the list filters re-dispatched `subscription_status` strings next to `accessState`, a second reading of the same rule.

## Decision
- `accessState` (`lib/billing.ts`, pure) returns a discriminated `kind` besides the old fields: `desativado`, `bloqueado`, `vitalicio`, `ativo`, `em_teste`, `teste_encerrado`, `carencia`, `atrasado_bloqueado`, `cancelado`, `desconhecido`. Precedence: deactivated (`desativada_em`, reason `desativada`), then manual block, then vitalício, then the stored status. Deactivation lives in the access rule too (revision of 15/10/2026), so `contaDesativada`, `processTurn`, the situation and the alerts all read `kind`. Every old case keeps its `blocked`, `reason`, `trialDaysLeft`, `warn` and `message` (proven in `e2e/central-clientes-conta.design.spec.ts`).
- `situacaoDaConta`, the "pagamento" alert and `FILTROS_DE_SITUACAO` (`lib/admin-alertas.ts`) MAP from `kind` (a table per kind; filters are sets of situations). Deactivation is the first kind. The list SQL (`admin_empresas_pagina`, `p_situacao`) repeats the same precedence: desativado, bloqueado, vitalicio, then the stored status.
- Storage: DEDICATED COLUMNS, not a new `subscription_status` value. `clients.vitalicio_desde` (vitalício) and `clients.bloqueado_em` (manual block), both `timestamptz`, null = no. Why this keeps one source of truth: each fact has ONE writer. `subscription_status`, `trial_ends_at`, `grace_until` are the gateway's state (the Asaas webhook and the subscribe route write them); vitalício and the manual block are the owner's decisions (only `admin_mudar_conta` writes them). A `lifetime` status would put both writers on one column: the webhook could overwrite the grant, and removing vitalício would have to invent which status to go back to (the previous one would be lost). With a column, removing vitalício just clears it and the real subscription state shows again. Access is still decided in ONE place, `accessState`, and `BillingRow` makes both columns REQUIRED so a gate that forgets to read them does not compile.
- The webhook never overwrites a vitalício company, in three layers: (1) the event map is the pure `atualizacaoDoEvento(evento, agora)` in `lib/billing.ts` (only event to update); the webhook's three tenant lookups select `id, vitalicio_desde`, and for a vitalício company it writes nothing and records `billing_events.error = 'ignorado: cliente vitalicio'`. (2) The trigger `clients_guarda_da_conta` RAISES `42501` for any write of `subscription_status`, `trial_ends_at` or `grace_until` outside the admin functions while the company is vitalício (first version reverted silently with a warning; changed in review so a buggy writer fails loudly, migration 20261015111730). (3) Even if the stored status changes, `accessState` puts vitalício before it. The subscribe route refuses to subscribe a vitalício company (409).
- The three marks (`vitalicio_desde`, `bloqueado_em`, `desativada_em`) change ONLY through `admin_mudar_conta`: the trigger raises `42501` for any other writer; the function turns the transaction-local `app.acao_admin` on just around its own update. Every action writes its `admin_acoes` row in the same transaction.
- Manual block (`bloquear`/`liberar`): read-only mode exactly like a blocked subscription (same four gates), reason `bloqueio_manual`, and it wins even over vitalício (it is a decision about ONE company).
- Financeiro actions (`PUT /api/admin/empresas/[id]/conta`): mark/remove vitalício (since the revision below, marking is an option of the "Estender teste" control; removing has its own button, shown only for a vitalício company) (refused with an Asaas subscription: vitalício is never charged, cancel first), extend trial (one control with the options 7 dias, 15 dias, Personalizado and Vitalício: `PRAZOS_DO_TESTE` and `acoesDoFinanceiro().estenderTeste` in `lib/admin-conta.ts`; the days go as `estender_teste`, Vitalício is the same `vitalicio` action; days only for `trialing` with a deadline; integer days from 1 up, counted from the later of the current end and now; no business upper bound exists, so none was invented; an out-of-range date answers 400), change plan (only `PLANS` keys; refused with a gateway subscription because the charged value would diverge), block/release. The tab shows the gateway ids masked on the server (`mascararId`, last 4) and the charges through the existing helper `subscriptionPayments` (first page Asaas returns).
- (Removed on 15/10/2026, kept for the record) BETA_ABERTO notice: while the switch was on, the list shows how many companies WOULD be blocked if it were turned off today. Counted by `admin_bloqueados_sem_beta` (one aggregate, no rows read), a SQL mirror of `accessState` without the switch, excluding companies already out for another reason (deactivated, manual block) and vitalício. The pure twin `cairiaSemBeta` (`lib/admin-alertas.ts`) feeds the preview and the tests; both files say they mirror `accessState`. Every new signup still gets the 7-day trial (`provision_tenant` unchanged). Removing the switch is a later step.

## Consequences
- A new access state means a new `kind`, a row in `SITUACAO_DO_TIPO`, a filter decision and the list SQL. The spec fails when a reachable situation is in no filter or in two.
- Writing `vitalicio_desde`, `bloqueado_em` or `desativada_em` by hand in SQL fails on purpose. A fix by hand means calling `admin_mudar_conta` (or setting `app.acao_admin` in that transaction, knowingly).
- While vitalício, any write of the subscription columns outside the admin functions fails (`42501`). In practice no path does it: the webhook skips vitalício, subscribing is refused, and a vitalício company cannot have a gateway subscription (marking is refused with one).
- The product owner logged into his OWN deactivated tenant is not barred from the app (so he can always reach the central), but his tenant gets the read-only mode of any blocked kind.
- Open for the owner: the manual-block message shown to the tenant ("Fale com a gente para liberar") has no support channel written; whether "Mudar plano" should also offer "sem plano"; an upper bound for extending a trial, if one is wanted.
- Evidence: rolled-back SQL run on 15/10/2026 (freeze kept `trialing` after an update to `canceled`, direct write of a mark raised `42501`, the count went 5 to 4 after extending one expired trial); `e2e/central-clientes-conta.design.spec.ts`, `e2e/central-clientes-acoes.design.spec.ts`, `e2e/central-clientes-conta.serial.spec.ts`.

## Revision 15/10/2026 (owner): the beta switch is removed
- The beta is over and Vitalício replaces the switch. `lib/beta.ts`, the `betaAberto` option and the `beta_aberto` kind of `accessState`, its readers (`getMyClient` in `lib/auth.ts`, `processTurn` in `lib/agent-turn.ts`), `cairiaSemBeta` and the central list notice (`/clientes` and the `/design/clientes?beta=` preview) are gone. `BETA_ABERTO` in the environment has no effect anymore (the owner can delete it in Vercel).
- Consequence the owner accepted: a company whose trial ended goes to the subscription screen (read-only mode) and its agent goes silent on WhatsApp, like any blocked kind. On 15/10/2026 four companies were in that state (expired trials); the owner marks Vitalício whoever must stay free.
- The SQL function `admin_bloqueados_sem_beta` stays in the database, unused by the new code: the code deployed before this revision still calls it on `/clientes`, so dropping it before the deploy would break that notice. Drop it in a later migration, after the deploy.
- "Estender teste" is one control with 7 dias, 15 dias, Personalizado and Vitalício (see the Financeiro actions above): same route, same SQL, same audit row, same refusals.
