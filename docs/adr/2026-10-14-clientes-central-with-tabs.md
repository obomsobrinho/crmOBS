# The product owner's central "Clientes": routes, per-route guard, list and detail with tabs
- Date: 2026-10-14
- Status: Accepted (owner decisions of 14/10/2026 in `docs/plano-central-clientes.md`; delivery 1 of 2, awaiting architect review)
- Area: admin, ui, data

## Context
The first slice of `/admin` (`docs/adr/2026-10-13-ai-usage-cap-in-tokens.md`) was one page, "Empresas", outside the app shell, with the AI cap edited in a dialog from the list. The owner wants ONE place to follow each company that uses the CRM (usage, health, plan and payment, later actions), reached from the menu, with a detail page per company, instead of separate admin pages. The companies' contacts list lived at `/clientes`, which is the natural name for this central ("Clientes" are the owner's customers), so the contacts moved.

## Decision
- Routes. `/clientes` (list) and `/clientes/[id]` (detail) are the owner's central, inside `app/(app)` so the menu and shell are the product's. The contacts list and ficha moved to `/contatos` and `/contatos/[id]` (screen name already "Contatos"; tables, `lib/clientes.ts` and the `clientes-*` data slots keep their names). `/admin` stays only as an address: the owner is redirected to `/clientes`, everyone else gets 404 as before. The preview of the contacts moved to `/design/contatos`; the central previews are `/design/clientes` and `/design/clientes/detalhe`.
- API path: kept under `/api/admin/*` (`empresas`, `empresas/[id]/{limite,uso,atendimento,whatsapp}`), not moved to `/api/clientes-central/*`. Reason: it is invisible to users, `proxy.ts` and the guard already cover the prefix, and moving it would only churn specs and the cap route that is already reviewed.
- The guard is PER ROUTE, with no shared prefix, and each kind has one helper in `lib/admin.ts` (both read `ehAdmin` over `ADMIN_USER_IDS` through `adminDaSessao`). Every API route is `export const GET|PUT = rotaDoAdmin(handler, opts)`: 404 for a non-admin, 400 for a malformed uuid, the handler receives the validated `id`; writes pass `revalidar: true`, the list `semId: true`. Every page under `app/(app)/clientes` starts with `await adminDaPagina(id?)`. `e2e/central-clientes-lib.design.spec.ts` lists the central pages and routes, asserts each one uses its helper (no hand-written 404 in a route, no `sessaoDaRota`, `revalidar` on writes), and fails when a new page or route is not in the list.
- Nothing reveals the central to a non-owner. API routes and `/admin`: 404 (proxy and route). Pages: a redirect decided on the server in ONE place, never 404 and never hidden UI (`adminDaPagina` calls `destinoDoNaoAdmin`; `proxy.ts` has no special case): `/clientes` goes to `/contatos`, `/clientes/[id]` goes to `/contatos/{id}` only when that id is a contact of the user's own tenant (with the user session so RLS decides), otherwise to `/contatos`. The same helper keeps the owner's own old contact bookmarks working (a numeric id is not a company id).
- Menu. "Clientes" is shown only to the product owner: `app/(app)/layout.tsx` computes `ehAdminPeloAmbiente(client.userId)` on the server and passes `ehAdmin` to `NavRail` (rail and mobile "Mais"). A convenience; the route guard is the lock.
- List. ONE keyset query evolved from `admin_empresas_pagina` (new `p_situacao` filter on the stored `subscription_status`, supported by the index `(subscription_status, name, id)`, plus `subscription_status`, `trial_ends_at`, `grace_until`, `created_at` and `tem_instancia`; and `p_id`, which returns ONE client through the same select. Every new parameter has a default, so callers of the earlier signature, including the code already in production, keep working; the old signatures were dropped and replaced, no data touched). Still 10 per page, infinite scroll (`usePaginada`), server search with debounce on `sem_acento(name)`, joins only after the limit, no realtime ("Atualizar"). Columns: client (plan, one alert chip), situation, WhatsApp, agent, AI usage in the month (bar, % of cap, US$), last activity. The whole row opens the detail. Filter chips (Todos, Em teste, Ativos, Atrasados, Cancelados) are the stored status, so "Em teste" also holds trials that already ended, which the row badge shows as "Teste encerrado". No counts on the chips (a counter would need its own aggregate; not asked).
- Situation and alerts live in ONE pure module, `lib/admin-alertas.ts`, over `accessState` (`lib/billing.ts`), the already computed `estadoDaIa` (`lib/custo-ia.ts`, it is passed in, never derived again), `montagemTerminada` (`lib/onboarding.ts`, also used by `montagemState`) and `diasDesde` (`lib/clientes.ts`, calendar days in Sao Paulo): no second formula. One `alertasDaEmpresa(item, agora, whatsapp?)` (`lib/admin-empresas.ts`) serves the list, `comLimite` and the detail. The situation does NOT pass `betaAberto`, otherwise every client would read "Beta aberto". Alert order (most urgent first, the first is the main one): IA stopped at the cap, payment late, WhatsApp down, near the cap, no activity for 7 days (the plan's number), setup not finished. "No activity" counts from the last agent turn or, if none, from the account creation, and only for a published and enabled agent.
- WhatsApp. The database stores no connection state, so the list never claims "connected or down": it says "Instância criada" or "Sem WhatsApp". The detail asks Evolution live, ONCE, from the browser (`GET /api/admin/empresas/[id]/whatsapp`; the state is normalized by the same pure function as the app banner, `lib/whatsapp-estado.ts`, and only `open` is connected; `estadoDaInstancia` in `lib/evolution.ts` reads it) and the result joins the alerts and the header when it arrives. Never one Evolution call per list row, never from a Server Component.
- Detail. Header (name, situation badge, main alert) and three tabs from the base layer. "Visão geral" comes from the server (`detalheDoCliente`: the same list select with `p_id`, one read of `prompt_mode` and `notify_group_jid`, and `tenant_members_do_cliente`). "Uso de IA" and "Atendimento" fetch on first open (`useCarga`); Atendimento brings the four panel periods in ONE response, so switching period fetches nothing. "Uso de IA": today, 7 days and month, the month bar per day, the weekday x hour grid (30 days), estimated US$ (`custoEstimadoUsd` with the model in use, unknown model is `null`), and the cap with its edit control (moved from the list; still `admin_mudar_limite_ia`, one transaction with the `admin_acoes` row). "Atendimento": conversations, the share the AI answered alone and the median first answer (`painel_janelas` through `metricsDaJanela`, who replied stays `lib/mensagem.ts`), AI replies and "passed to the team", help requests by reason (`painel_motivos`, `lib/motivos.ts`) and by solution (`admin_cliente_solucoes`, `contagemPorSolucao` in `lib/solucoes.ts`), both drawn by `ListaDeContagens` (shared with the panel's "Por que a IA te chamou"), and the saved rules count (`normalizarRegras(regras_salvas)`).
- Aggregates are SQL over indexed columns, service_role only, bounded windows, SP dates (`admin_cliente_uso` reads `agent_turns(client_id, created_at)` over 31 days and counts turns that called the model, bench included, the same condition `logTurn` uses to add to the monthly counter). Nothing counts rows in memory.

## Revision (15/10/2026)
The owner asked for a richer dashboard on screen. The "Uso de IA" and "Atendimento" tabs now use real charts, a period filter and the hourly Dia period: see `docs/adr/2026-10-15-charts-recharts-in-base-layer.md`. The "Uso de IA" description above (today / 7 days / month tiles, one bar per day of the month, hand-made grid) is superseded by it.

## Consequences
- The contacts URL changed (`/clientes` to `/contatos`); old links keep working through the redirects above. Specs, `NavRail`, `ListaClientes`, `NovoClienteDialog` and the previews follow the new paths.
- The cap decides the stop through `consumo_ia_mensal`; the Uso de IA charts sum `agent_turns`. They differ for the month that holds turns from before the counter existed (it started with no backfill), and the screen says the cap counts by the monthly counter.
- `painel_janelas` always includes the accumulated window 0 (a scan of the tenant's messages), so the Atendimento tab costs what one visit of the tenant's own panel costs. It runs ONCE per opening (the four periods go to the database as four windows of one call to `painel_janelas`, one to `painel_motivos` and one to `admin_cliente_solucoes`, through the panel's own loader `carregarJanelasDoPainel`), on demand, one client at a time, lazily on the tab. A bounded variant was not built to avoid a fourth copy of "who replied" in SQL.
- "Last activity" is the last `agent_turns` row, bench included (as shipped in the first slice), so a bench test counts as activity.
- The owner login has no name stored (signup takes company name and e-mail): the "Visão geral" shows the owner's e-mail.
- Delivery 2 is out of this ADR: tab Financeiro and its actions, Vitalício in the access rule, the `BETA_ABERTO` notice, tab Ações (Desativar, Reativar, Apagar de vez). Delivery 2 (15/10/2026): `docs/adr/2026-10-15-vitalicio-replaces-the-beta-switch.md` (situation and filters now map from `accessState().kind`, which supersedes the "filter chips are the stored status" line above) and `docs/adr/2026-10-15-two-step-company-deletion.md`.
- Tests: `e2e/central-clientes.design.spec.ts` (list: 10 per page, rolling, situation, alert chips, cost, search, filter, row link, empty, no dashes, mobile; hidden menu item on desktop and mobile; detail: header, Visão geral, live WhatsApp, Uso de IA sums and grid, editing the cap, Atendimento numbers per period, lazy tabs; anonymous requests: 404 for `/admin` and the API, `/clientes` goes to `/login` and never 404; the Contatos naming), `e2e/central-clientes-lib.design.spec.ts` (situation, alerts, usage, attendance, per-route guard), `e2e/atendente.att.spec.ts` (non-admin: redirects and 404s; login suite, not run by the delivery agent).
