# AI usage per company with a monthly cap in tokens, and the first slice of /admin
- Date: 2026-10-13
- Status: Accepted (owner approved `docs/plano-custo-ia.md` on 13/10/2026; awaiting architect review)
- Area: agent-ai, admin, data

## Context
P1 item 6 (`docs/proximos-passos.md`). The beta is paid by the owner: every AI reply on every tenant's WhatsApp is billed to his OpenAI account, and nobody saw how much each company spent. A tenant in a loop or with heavy volume grew the bill with no brake.

Measured baseline (OBM, last 30 days, `agent_turns`, real turns only): model `gpt-5.4-mini`; per turn about 4,683 input tokens (about 2,304 of them cached) and 83 output tokens. Official price (developers.openai.com/api/docs/pricing, read on 13/10/2026), per 1M tokens: input US$ 0.75, cached input US$ 0.075, output US$ 4.50. Cost per turn about US$ 0.0023 (about 430 replies per US$ 1). A small company (50 replies a day, about 1,500 a month) costs about US$ 3.50; a busy one (240 a day) about US$ 17. US$ 50 per company was far too high for the beta; the default cap is about US$ 5.

Measured at delivery (October 2026 up to the 13th): OBM spent about 12.4M tokens, of which about 12.3M were bench turns (`dry_run`, mostly the paid test suites) and 0.14M real turns.

## Decision
- The cap is in TOKENS (input including cached, plus output), not money. Default `LIMITE_PADRAO_TOKENS = 10_000_000` per company per calendar month of America/Sao_Paulo (`mesSP`); `clients.ia_limite_tokens` null means the default. The screen shows an ESTIMATED cost in US$ from `PRECOS_POR_MODELO` (source URL and date in code); a model outside the table is `null`, never a guess. No BRL, no exchange rate.
- One pure module, `lib/custo-ia.ts`: prices, `custoEstimadoUsd`, `limiteDaEmpresa`, `tokensUsados`, `estadoDoConsumo` (`normal` below 80%, `aviso` from 80%, `parado` at or above the cap), `mesSP`, `estadoDaIa` for the admin, screen formats and the stop texts. Server and browser use it; the I/O lives in `lib/consumo-ia.ts` (server-only).
- Counter: `consumo_ia_mensal (client_id, mes, tokens_entrada, tokens_cache, tokens_saida, atualizado_em)`, PK `(client_id, mes)`. `logTurn` calls `somar_consumo_ia` (one atomic upsert, in parallel with the `agent_turns` insert, best-effort, never throws) for every turn that called the model, bench (`dryRun`) included. The turn check is ONE PK read (`lerConsumoDoMes`), run in the same `Promise.all` as the `clients` select (no extra round trip); never a sum over `agent_turns`. The counter starts at zero from this delivery (no backfill): a backfill of October would have stopped OBM immediately with test usage.
- Turn path (`processTurn`): after the notices-number, subscription and agent-switch gates and before persona, RAG and model, in WhatsApp AND bench turns: if the month is `parado`, return the silent turn (`diagnostics.limiteIa`, `agent_turns.silenced = 'limite_ia'`), same 200 contract as the agent switch, so n8n still records the customer message. A failed read attends (better one turn over the cap than a muted company). The month is the real clock, never `agoraTeste`. `/api/conversations/orientar` checks the month first and refuses BEFORE closing the request (409, `motivo: "limite_ia"`, text `TEXTO_ORIENTAR_NO_LIMITE`): the request stays open and Pedidos and the conversation composer show "A IA está parada no limite de uso do mês. Responda pela conversa ou peça para aumentar o limite." The bench shows the stop text as its error.
- Notices: one sender, `agendarAvisoDeConsumo` (`lib/consumo-ia.ts`), called only from `processTurn`, via `after()`, and ONLY for a real WhatsApp turn: the pure `podeAvisarConsumo` (`lib/custo-ia.ts`) says never for `dryRun` and never for a DDD 00 phone (architect review: the paid suites run through the bench on OBM, and no automated test may cause an Evolution call, docs/adr/2026-10-03-test-phone-never-reaches-evolution.md). Bench turns still count and are still blocked; when a bench turn crosses a line, the first real turn afterwards sends the pending notice. Architect review: the marks live in `consumo_ia_mensal` (`aviso_80_em`, `aviso_100_em`; the first-cut table `consumo_ia_avisos` and `marcar_aviso_consumo` were dropped in `20261013232131_avisos_no_consumo_e_limite_atomico.sql`). The turn's PK read (and the sum's return) carry the marks, and the pure `avisoPendente` says whether the current level is still unmarked, so once notified no message writes anything. `reivindicar_aviso_consumo` (conditional update where the mark is null) decides who sends; if every attempted send fails, `liberar_aviso_consumo` sets the mark back to null and the next real turn retries (a partial success keeps the mark, to avoid repeating to who already received; no destination at all keeps it too, with a log). The stopped path also tries a pending `parado` (covers a cap lowered below usage and a crossing made by the bench). The text is `textoDoAvisoDeConsumo` (`lib/avisos.ts`). Destinations: the company's `notify_group_jid` through its instance, and the owner, through the `notify_group_jid` and instance of each admin user's own tenant (one `user_clients` query with `clients` embedded, oldest tenant picked in memory, the same choice as `getMyClient`), skipped and logged when missing, never duplicated when it is the same destination (`mesmoDestino`, phone key with the ninth digit). A bench turn or a DDD 00 phone never sends and never marks. Sends run after the reply (`after()`), best-effort.
- `/admin` (first slice of Admin v1), guarded by `ADMIN_USER_IDS` (server env, comma-separated `auth.users.id`, never hard-coded, never a DB column): `proxy.ts` answers 404 for `/admin` and `/api/admin/*` to anyone else (no login included), the page calls `notFound()` and each route answers 404 (`adminDaSessao`, `lib/admin.ts`; writes reconfirm the session with `getUser()`). Without the env var nobody is admin. The admin routes do not use `sessaoDaRota`: the admin acts across tenants, not as a member of one.
- Admin list "Empresas" (`components/admin/ListaEmpresas.tsx`, `lib/admin-empresas.ts`): `admin_empresas_pagina` (service_role, keyset by name and id, 10 per page, trigram search on `sem_acento(name)`, the month counter and the last `agent_turns` row joined only after the limit), infinite scroll with `usePaginada`, server search with debounce, no realtime (an "Atualizar" button). Columns: name, account type and plan, AI state (Ativa, Perto do limite, Parada no limite, Desligada), tokens and % of the cap with a bar (brand, warn, danger), estimated US$ (model in use, `AGENT_MODEL`), cap (editable), last activity (last agent turn, bench included).
- Editing the cap: `PUT /api/admin/empresas/[id]/limite` (`{ limite: tokens | null }`, integer 1 to 1 billion; malformed id 400) calls ONE function, `admin_mudar_limite_ia`, in one transaction: locks the `clients` row, writes `ia_limite_tokens`, inserts `admin_acoes (quem, acao, alvo, antes, depois, em)` and clears this month's marks whose threshold (computed by `limiaresDoLimite`; the app stays the only source of 80%/100%) is now above the usage, so re-crossing notifies again. The field is always in millions of tokens ("10", "2,5" or "2.5", comma or point is the decimal mark) and shows the resulting tokens under it; the first cut read "0.5" as 5 million. Raising above the usage reactivates on the next message (the turn reads the cap every time; there is no stop state to clear).
- Company side: `components/BannerLimiteIa.tsx` in the app shell (`app/(app)/layout.tsx`, inside `Suspense`, ONE read on the server: the month row with the cap embedded through the FK; no row means `normal`) while `parado`, for owner and attendants. The cap column is readable by the tenant through the table SELECT grant and RLS (its own value only); no screen shows it.
- Naming: in the companies' app the contacts list is "Contatos" (menu, mobile "Mais", title, empty states, "Novo contato", search label, back link). Tables, lib modules and the `/clientes` route are unchanged (route rename is a later step). In the admin the tenants are "Empresas".
- Out of scope: Whisper transcription and knowledge-base embeddings are not counted per company yet.
- Base layer: the search frame copied in five screens became `CampoBusca` and the usage bar (admin and "Por que ela te chamou") became `Medidor` (`components/ui/`).

## Consequences
- The paid suites (`ia`, `bateria`, `n8n`) and the owner's bench run on the test tenants and now count. At October's pace OBM would cross the default cap: the owner should raise OBM's cap in `/admin` (the code never bypasses the check for tests). A crossing caused by the bench sends nothing; the notice goes out on the next real WhatsApp turn of that company.
- The estimated cost uses the model in use at read time for the whole month; if `OPENAI_AGENT_MODEL` changes mid-month the estimate is approximate (tokens, the real cap, stay exact).
- One extra PK read per turn (parallel to the tenant read) and one per app navigation (banner, off the critical render path).
- Known gaps: concurrent turns near the cap all pass the check before any of them sums, so a company can overshoot the cap by a few turns (a turn is about 4.8k tokens); a model reply that cannot be parsed (`AgentError` before `logTurn`), RAG query embeddings and Whisper transcriptions are not counted.
- Tests: `e2e/custo-ia.design.spec.ts` (cost math against the table, thresholds, SP month boundary, unknown model, `podeAvisarConsumo`, admin list parsing, texts without dashes), `e2e/admin.design.spec.ts` (`/design/admin` list, bar states, edit, empty; banner and "Contatos" on `/design/clientes?ia=parada`), `e2e/custo-ia.serial.spec.ts` (atomic sum, claim once and release, the admin function changing the cap with its audit row and clearing marks in one transaction, a stopped bench turn with a non test phone marks no notice, silent `limite_ia` in WhatsApp and bench turns with no model call and no notice for the DDD 00 phone, banner on and off after raising the cap; restores cap and tokens), `e2e/atendente.att.spec.ts` (404 on `/admin` and the admin routes).
