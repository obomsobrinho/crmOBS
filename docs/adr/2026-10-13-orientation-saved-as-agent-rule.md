# An orientation can be saved as a permanent agent rule
- Date: 2026-10-13
- Status: Accepted (owner approved the design, the limits and the own section in guided mode; architect review applied)
- Area: agent-ai, pedidos, data

## Context
P1 item 5 (`docs/proximos-passos.md`): when the team orients the AI on a help request (`POST /api/conversations/orientar`, `handoffs.instruction`, `solucao = orientou_ia`), the orientation is valid for that conversation only. The same question comes back in the next conversation and the owner has to orient again. The owner approved (13/10/2026): a "Salvar como regra" action on the resolved request, an editor pre-filled with the orientation so the owner generalizes it before saving ("Diga ao João que chega amanhã" is not a rule; "frete grátis acima de R$ 200" is), the rule enters the prompt in both builder modes, it counts in `LIMITS.persona`, its values count as a guardrail source, and every save is a publication.

The first cut stored the list inside `agent_config.regrasSalvas`. The architect review found that this coupled the rules to the agent-config save (the `PUT` had to merge the key back, an advanced tenant with `agent_config` null stopped being "manual" after a rule and lost the overwrite confirmation) and allowed lost updates between two concurrent saves. The list moved to its own column.

## Decision
- Storage: `clients.regras_salvas jsonb not null default '[]'` (array of strings, `check` on the type; migration `20261013211408_clients_regras_salvas.sql`, which also backfilled and removed any `agent_config.regrasSalvas`). Read by the owner's session through the existing table SELECT and tenant RLS; never written by the browser (`clients` has no UPDATE for `authenticated`).
- Limits (owner approved): one rule is at most `LIMITS.bullet` (200) characters, measured by `tamanhoDaRegra` on the screen counter and in the route; longer is REFUSED (400), never truncated. At most `MAX_REGRAS_SALVAS` (20), the same cap as the other form lists.
- Normalization in ONE place: `normalizarRegras` (`lib/agent-prompt.ts`, pure: strings only, one line, `sanitizeText`, no empties, no duplicates), applied at the borders (DB read, request body). `blocoRegrasSalvas` trusts its input. The pure list decision is `mudarRegras` (empty, too long, full, absent; adding an existing rule is `mudou: false`, not an error).
- Prompt: ONE function, `blocoRegrasSalvas`, renders `### REGRAS SALVAS PELO TIME` (a fixed opening line, then `- rule` items) at the end of the tenant content, right before the base tail, in both modes (owner approved the own section in guided mode instead of the "O que o agente NÃO deve fazer" list, which would show a positive rule as a prohibition). `compilePersona` takes `regrasSalvas` in both modes, and ONE helper, `compilarDoTenant(row, regrasOverride?)`, compiles a `clients` row (dispatch by `prompt_mode`, `handoffNotice`, rules from the column or the new list); `personaDoTenant` and the rules route use it. The agent-config `PUT` and the bench compile the config IN EDIT, so they call `compilePersona` with the column's rules.
- Advanced strip: `stripBaseTail` always cuts a section titled `REGRAS SALVAS PELO TIME` (the compiled `clients.persona` contains the generated copy). The generated copy (fixed opening line plus only `- ` items) goes silently; anything else under that title is the owner's text and is reported in `removed`, so the UI warns.
- Single writer: only `POST/DELETE /api/clients/[id]/agent-rules` changes the list (`sessaoDaRota` with `dono`, `ativa` and `revalidar`). It reads the row, decides with `mudarRegras`, recompiles with `compilarDoTenant`, refuses over `LIMITS.persona` (400 with the resulting size; a DELETE is always accepted because it only shrinks) and returns `aviso` above `LIMITS.personaWarn`. The write is a COMPARE AND SWAP: `trocar_regras_salvas(p_client, p_antes, p_depois, p_persona_antes, p_persona)` (service_role only) updates `regras_salvas` and `persona` only if both are still what the route read (`20261013211807_trocar_regras_salvas_persona_nula.sql` treats a null persona as ''). On `false` (another save in between: two tabs, a double click, a form Save) the route rereads and retries once, then answers 409 "Tente de novo". It never touches `agent_config` and never overwrites a newer save. After the swap, `registrarPublicacao` (`lib/publicacoes.ts`, shared with the `PUT`) and the request mark run in `Promise.all`.
- The same rule saved again (from another request) is a success: no swap, no new version, the request is marked, and the answer says "Essa regra já estava salva".
- Agent-config `PUT`: knows nothing about writing rules (no merge). It reads `regras_salvas` only to compile and to enforce `LIMITS.persona`; over the limit with rules present, the message says the saved rules count and that deleting some frees space.
- Request mark: `handoffs.regra_salva_em` (migration `20261013154539_handoff_regra_salva_em.sql`, select grant to `authenticated`, written only by service_role), set by the POST when `pedidoId` is a request of the same tenant resolved by orientation with an instruction. `pedidos_pagina` is untouched: `FontePedidos.historia` reads the column in the SAME `Promise.all` as the messages, only for `podeVirarRegra` requests, so the action appears with the sections (no separate request, no flash).
- Screens: `components/SalvarComoRegra.tsx` inside the "Orientação do time" section (`SecoesDoPedido` render prop `acaoDaOrientacao`), shown only to the owner of an active account; nothing is saved without the explicit "Salvar regra" click on the edited text; Cancel restores the orientation text. `/agente` lists and deletes the rules in both modes (`components/agente/RegrasSalvas.tsx`, guided under "O que ele pode fazer", advanced under the hand-written prompt); deleting publishes immediately, behind a confirmation. The form hook keeps the list only for the prompt preview and the bench.
- Bench: `POST /api/playground` uses `regrasSalvas` from the body when present (normalized), otherwise reads the tenant's column. The fixed-config suites (`ia`, `bateria`, the `fluxos-beta` bench calls) send `regrasSalvas: []` so their configuration stays fixed.
- Guardrail: no code change. The rules are part of the compiled persona, which is already a source (`applyGuardrail`), so "R$ 200" in a saved rule lets the AI say it; proven by `e2e/regras-salvas.design.spec.ts` (the same reply is blocked without the rule).

## Consequences
- Every saved rule costs prompt budget on every turn. OBM (advanced) was about 14.7k of 16k on 2026-10-13: roughly 1.3k left, a handful of rules. The guided `/design/agente` mock sits about 100 characters under the warning, so its sample rules are opt-in (`?regras=1`).
- A rule is tenant content: `### PRECEDÊNCIA` of the base still wins over it.
- Skipped on purpose (architect): storing the advanced raw text separately from the compiled record (pre-existing design, too large) and moving the rules after the base tail (would break the cacheable prefix).
- Tests: `e2e/regras-salvas.design.spec.ts` (assembly in both modes, `compilarDoTenant`, owner-written section warned, limit, normalization, list, guardrail, screens including the over-limit editor), `e2e/regras-salvas.serial.spec.ts` (DB round trip on the OBS tenant, repeated rule from another request, restores the list and the persona, deletes every publication it created), `e2e/atendente.att.spec.ts` (403 for the attendant with an empty body, no write possible).
