# Central "Clientes" (product owner only; evolves `/admin`)

In the central the companies that use the CRM are "clientes" (the tenants, `clients`). Never confuse with the tenant's contacts, which are "Contatos" (`/contatos`, `dados_cliente`).

## Access
- Admin = a user id listed in the server env `ADMIN_USER_IDS` (comma-separated `auth.users.id`), decided ONLY by `ehAdmin` (`lib/admin-acesso.ts`, pure). Never a DB column a tenant could change, never an id written in code. Without the env var nobody is admin.  (why: docs/adr/2026-10-13-ai-usage-cap-in-tokens.md)
- Routes: `/clientes` (list) and `/clientes/[id]` (detail, `?aba=visao|uso|atendimento`) live in `app/(app)/clientes` inside the app shell; `/admin` only redirects the owner to `/clientes`. The API stays under `/api/admin/*` (path is invisible to users; chosen to keep the guard and the specs untouched): `empresas` (list), `empresas/[id]/{limite,uso,atendimento,whatsapp}`.  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)
- The guard is PER ROUTE, there is no shared prefix, and each kind has ONE helper in `lib/admin.ts`: every `/api/admin/*` route is `export const GET|PUT = rotaDoAdmin(handler, opts)` (404 for a non-admin, 400 for a malformed uuid, hands the handler the validated `id`; `revalidar: true` for a route that WRITES, `getUser()`; `semId: true` for the list), and every page under `app/(app)/clientes` starts with `await adminDaPagina(id?)`. `/admin` calls `adminDaSessao` itself (404 for non-admin, redirect for the owner). `e2e/central-clientes-lib.design.spec.ts` lists the central pages and routes and fails when one does not use its helper (and when a new one is not in the list). Admin routes do not use `sessaoDaRota` (the admin acts across tenants, not as a member of one).  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)
- Non-admins never learn the central exists. API routes and `/admin`: 404 (`proxy.ts` answers 404 for `/admin` and `/api/admin/*` to anyone else, no login included; each route answers 404 again). Pages `/clientes` and `/clientes/[id]`: NO 404, a redirect decided on the server in ONE place (`adminDaPagina` -> `destinoDoNaoAdmin`, no special case in `proxy.ts`): `/clientes` goes to `/contatos`, `/clientes/[id]` goes to `/contatos/{id}` only when that id is a contact of the user's own tenant (RLS with the user session), otherwise `/contatos`; an admin opening a non-uuid id (an old contact link) takes the same path. Hiding UI is never the enforcement.  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)
- The menu item "Clientes" (`components/NavRail.tsx`, `adminOnly`, mobile "Mais" too) shows only when `app/(app)/layout.tsx` passes `ehAdmin` (server decision from `ehAdminPeloAmbiente(client.userId)`). It is a convenience; the route guard is the lock.  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)
- Reads and writes go through `service_role` on the server only (`lib/admin.ts`, admin routes); the browser talks only to `/api/admin/*`. Never import `lib/supabase/service` in `components/admin/**`.  (why: docs/adr/2026-10-13-ai-usage-cap-in-tokens.md)
- Every admin change and its `admin_acoes` row (`quem`, `acao`, `alvo`, `antes`, `depois`, `em`) happen in ONE SQL function, one transaction (cap: `admin_mudar_limite_ia`, which locks the `clients` row and clears stale notice marks). Never two writes from the route. No admin action without a trace.  (why: docs/adr/2026-10-13-ai-usage-cap-in-tokens.md)
- Validate every id, cursor, period and filter param (`ehUuid`, `ehPeriodo`, `ehFiltroDeSituacao`): 400 on malformed, never 500. The page size `n` is clamped only in SQL.  (why: docs/adr/2026-10-13-ai-usage-cap-in-tokens.md)

## List
- Production loading rules: `admin_empresas_pagina` (ONE keyset query by name and id, 10 per page, trigram search on `sem_acento(name)`, filter by stored `subscription_status` with the index `(subscription_status, name, id)`, joins only after the limit; `p_id` returns ONE client through the same select, which is how the detail builds its row; every parameter has a default so older callers keep working), `usePaginada` with infinite scroll, server search with debounce, no realtime (an "Atualizar" button). Never an N+1 per row and NEVER a call to Evolution per row: the database does not store the WhatsApp connection, so the list says only "Instância criada" or "Sem WhatsApp".  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)
- Row math (state, %, estimated cost, situation, alerts) only through `paraEmpresa`/`comLimite`/`alertasDaEmpresa` (`lib/admin-empresas.ts`; the list, `comLimite` and the detail all use `alertasDaEmpresa`) over `lib/custo-ia.ts`, `lib/billing.ts` (`accessState`) and `lib/admin-alertas.ts`, which receives the already computed `estado` of the AI and never derives it again. The situation does NOT pass `betaAberto`. Alert rules live ONLY in `lib/admin-alertas.ts` (order: IA stopped at the cap, payment late, WhatsApp down, near the cap, no activity for 7 days, setup not finished); never a second formula in SQL, a route or a component.  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)

## Detail
- Header (name, situation badge, main alert) and tabs from the base layer (`Tabs`, `Badge` `estado-*`, `Stat`, `Medidor`). "Visão geral" comes from the server (`detalheDoCliente`: one read per table by key); "Uso de IA" and "Atendimento" load on first open through `/api/admin/empresas/[id]/{uso,atendimento}` (`useCarga`, `lib/use-carga.ts`; Atendimento brings the FOUR panel periods in one read, so switching period fetches nothing); the WhatsApp state is read live ONCE by the browser (`/api/admin/empresas/[id]/whatsapp`, never from a Server Component) and joins the alerts when it arrives.  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)
- Aggregates come from SQL functions over indexed columns, service_role only, bounded windows, dates in `America/Sao_Paulo`: `admin_cliente_uso` (per day and weekday x hour over `agent_turns`, 31 and 30 days), `admin_cliente_uso_horas` (per hour, capped at 48 hours in the function, for the Dia period; additive, never change `admin_cliente_uso`'s signature), `admin_cliente_solucoes` (help requests by stored solution, the four windows as arrays), plus the panel's `painel_janelas` (through the same loader, `carregarJanelasDoPainel`), `painel_motivos` and `painel_series` (`carregarSeriesDoPainel`, the columns of the replies chart through `barrasDasSeries`) for the Atendimento tab (one call each, four windows) (who replied, median first answer, reasons; never a second formula, `lib/mensagem.ts` stays the only rule). Never fetch rows to count in memory.  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)
- "Uso de IA" and "Atendimento" share ONE period filter (`SeletorDePeriodo`, `components/painel/SeletorDePeriodo.tsx`, the chips and keys of `lib/periodo.ts`, the SAME piece `/painel` uses; tab indicators are `Indicador` in `components/admin/pecas.tsx`) and both bring the four periods in one read. "Uso de IA": ONE chart (columns of tokens per hour for Dia, per day for the others, plus the dashed monthly-limit pace line `ritmoDoLimite` = cap / days of the month, / 24 per hour; the cap meter and "Editar limite" live in the same card), four tiles that follow the chip, and the weekday x hour heatmap (30 days, does not follow the chip). "Atendimento": four numbers plus stacked columns (AI and team replies), a donut (resolutions) and horizontal bars (reasons). Charts per `ui.md`; a new central chart needs a text table view and a tooltip test.  (why: docs/adr/2026-10-15-charts-recharts-in-base-layer.md)
- The cap is edited in the "Uso de IA" tab (`EditarLimiteDialog`, one transaction with the `admin_acoes` row). The cap counter (`consumo_ia_mensal`) decides the stop; the charts sum the registered turns (`agent_turns`), and the screen says so.  (why: docs/adr/2026-10-13-ai-usage-cap-in-tokens.md)
- Previews with fake data: `/design/clientes` (list) and `/design/clientes/detalhe?cliente=&aba=&whatsapp=&vazio=` (detail), both `notFound()` in production. They run the SAME functions (`paraEmpresa`, `usoParaTela`, `atendimentoDe`).
