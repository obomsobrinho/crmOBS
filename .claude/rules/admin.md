# Central "Clientes" (product owner only; evolves `/admin`)

In the central the companies that use the CRM are "clientes" (the tenants, `clients`). Never confuse with the tenant's contacts, which are "Contatos" (`/contatos`, `dados_cliente`).

## Access
- Admin = a user id listed in the server env `ADMIN_USER_IDS` (comma-separated `auth.users.id`), decided ONLY by `ehAdmin` (`lib/admin-acesso.ts`, pure). Never a DB column a tenant could change, never an id written in code. Without the env var nobody is admin.  (why: docs/adr/2026-10-13-ai-usage-cap-in-tokens.md)
- Routes: `/clientes` (list) and `/clientes/[id]` (detail, `?aba=visao|uso|atendimento|financeiro|acoes`) live in `app/(app)/clientes` inside the app shell; `/admin` only redirects the owner to `/clientes`. The API stays under `/api/admin/*` (path is invisible to users; chosen to keep the guard and the specs untouched): `empresas` (list), `empresas/[id]/{limite,uso,atendimento,whatsapp,conta,cobrancas,exportar,apagar}`.  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md, docs/adr/2026-10-15-two-step-company-deletion.md)
- The guard is PER ROUTE, there is no shared prefix, and each kind has ONE helper in `lib/admin.ts`: every `/api/admin/*` route is `export const GET|PUT = rotaDoAdmin(handler, opts)` (404 for a non-admin, 400 for a malformed uuid, hands the handler the validated `id`; `revalidar: true` for a route that WRITES, `getUser()`; `semId: true` for the list), and every page under `app/(app)/clientes` starts with `await adminDaPagina(id?)`. `/admin` calls `adminDaSessao` itself (404 for non-admin, redirect for the owner). `e2e/central-clientes-lib.design.spec.ts` lists the central pages and routes and fails when one does not use its helper (and when a new one is not in the list). Admin routes do not use `sessaoDaRota` (the admin acts across tenants, not as a member of one).  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)
- Non-admins never learn the central exists. API routes and `/admin`: 404 (`proxy.ts` answers 404 for `/admin` and `/api/admin/*` to anyone else, no login included; each route answers 404 again). Pages `/clientes` and `/clientes/[id]`: NO 404, a redirect decided on the server in ONE place (`adminDaPagina` -> `destinoDoNaoAdmin`, no special case in `proxy.ts`): `/clientes` goes to `/contatos`, `/clientes/[id]` goes to `/contatos/{id}` only when that id is a contact of the user's own tenant (RLS with the user session), otherwise `/contatos`; an admin opening a non-uuid id (an old contact link) takes the same path. Hiding UI is never the enforcement.  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)
- The menu item "Clientes" (`components/NavRail.tsx`, `adminOnly`, mobile "Mais" too) shows only when `app/(app)/layout.tsx` passes `ehAdmin` (server decision from `ehAdminPeloAmbiente(client.userId)`). It is a convenience; the route guard is the lock.  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)
- Reads and writes go through `service_role` on the server only (`lib/admin.ts`, admin routes); the browser talks only to `/api/admin/*`. Never import `lib/supabase/service` in `components/admin/**`.  (why: docs/adr/2026-10-13-ai-usage-cap-in-tokens.md)
- Every admin change and its `admin_acoes` row (`quem`, `acao`, `alvo`, `antes`, `depois`, `em`) happen in ONE SQL function, one transaction (cap: `admin_mudar_limite_ia`, which locks the `clients` row and clears stale notice marks; account actions: `admin_mudar_conta`, whose `mudar_plano` is followed by `alinharMarcasDoMes` because the cap follows the plan; purge: `admin_apagar_cliente`; the LGPD export also leaves a row, `admin_registrar_exportacao`). Never two writes from the route. No admin action without a trace.  (why: docs/adr/2026-10-13-ai-usage-cap-in-tokens.md)
- Validate every id, cursor, period and filter param (`ehUuid`, `ehPeriodo`, `ehFiltroDeSituacao`): 400 on malformed, never 500. The page size `n` is clamped only in SQL.  (why: docs/adr/2026-10-13-ai-usage-cap-in-tokens.md)

## List
- Production loading rules: `admin_empresas_pagina` (ONE keyset query by name and id, 10 per page, trigram search on `sem_acento(name)`, filter by situation (ONE icon button next to the search that opens the situation list and shows a "1" while a filter is active; `p_situacao`: the stored `subscription_status` with the index `(subscription_status, name, id)`, or the marks vitalicio, bloqueado, desativado with partial indexes; precedence in the Financeiro section below), joins only after the limit; `p_id` returns ONE client through the same select, which is how the detail builds its row; every parameter has a default so older callers keep working), `usePaginada` with infinite scroll, server search with debounce, no realtime (an "Atualizar" button). Never an N+1 per row and NEVER a call to Evolution per row: the database does not store the WhatsApp connection, so the list says only "Instância criada" or "Sem WhatsApp".  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)
- Row math (state, %, estimated cost, situation, alerts) only through `paraEmpresa`/`comLimite`/`alertasDaEmpresa` (`lib/admin-empresas.ts`; the list, `comLimite` and the detail all use `alertasDaEmpresa`) over `lib/custo-ia.ts`, `lib/billing.ts` (`accessState`) and `lib/admin-alertas.ts`, which receives the already computed `estado` of the AI and never derives it again. Alert rules live ONLY in `lib/admin-alertas.ts` (order: IA stopped at the cap, payment late, WhatsApp down, near the cap, no activity for 7 days, setup not finished); never a second formula in SQL, a route or a component.  (why: docs/adr/2026-10-14-clientes-central-with-tabs.md)

## Financeiro and Ações (delivery 2)
- Situation, the payment alert and the list filters MAP from `accessState().kind` (`SITUACAO_DO_TIPO`, `FILTROS_DE_SITUACAO` as sets of situations in `lib/admin-alertas.ts`); never re-read `subscription_status` in a screen, route or alert. Deactivated (`desativada_em`) comes first and has no alerts. `admin_empresas_pagina` (`p_situacao`: `vitalicio`, `trialing`, `active`, `past_due`, `canceled`, `bloqueado`, `desativado`) repeats the precedence desativado, bloqueado, vitalicio, status; change both together.  (why: docs/adr/2026-10-15-vitalicio-replaces-the-beta-switch.md)
- Every account action is `PUT /api/admin/empresas/[id]/conta` (`{ acao, dias?, plano? }`, validated by `pedidoDeAcao`, `lib/admin-conta.ts`) into `admin_mudar_conta` (one transaction, `admin_acoes` row); SQL answers (`ok`, `sem_mudanca`, refusals) map ONLY through `respostaDoSql`, purge stops through `respostaDoApagar` (`PARADAS_DO_APAGAR`). The route answers the client re-read by `empresaEFinanceiro`; if that re-read fails AFTER the write committed, it answers success with `recarregue: true`, never "nada foi mudado". The screen never recomputes the row, and which Financeiro actions are allowed (and the refusal text) comes ONLY from `acoesDoFinanceiro` (mirror of the SQL refusals, text from `RESPOSTA_DO_SQL`). Vitalício and plan change are refused with a gateway subscription; extend trial only for `trialing` with a deadline, integer days from 1, no invented upper bound. The Assinatura card shows only the dates of the situation (`linhasDaAssinatura(conta, kind)`: the trial end only in trial, the grace only with late payment, "Vitalício desde" and "Bloqueado desde" only when the mark exists); the provider card exists only when `provedor` is set and lists only the ids that exist, and with no provider the Cobranças card carries ONE line (`textoSemAssinatura`: "Sem cobrança: conta vitalícia." or "Sem assinatura no Asaas."). A successful action writes no "feito" text (the screen updates); only the preview and "recarregue" notes remain. "Estender teste" is ONE control with 7 dias, 15 dias, Personalizado and Vitalício (`PRAZOS_DO_TESTE`, `acoesDoFinanceiro().estenderTeste`: days as `estender_teste`, Vitalício as the same `vitalicio` action); "Remover vitalício" shows only for a vitalício company. The Ações card of Financeiro shows ONLY what can be done now: a refused action has no (greyed) button, it becomes one muted line with the reason, and actions refused for the same reason share one line (`recusasAgrupadas`, text from `RESPOSTA_DO_SQL`); the provider shows by display name (`nomeDoProvedor`: "Asaas"), never the raw key. Gateway ids reach the browser only masked (`financeiroDe`, `mascararId`); charges come only from the existing `subscriptionPayments`.  (why: docs/adr/2026-10-15-vitalicio-replaces-the-beta-switch.md)
- "Ações" is the danger zone, its own tab. Desativar/Reativar is reversible and enforced on the server (`barrarContaDesativada` in pages, `sessaoDaRota` 403, `processTurn` silent turn); the product owner (`ADMIN_USER_IDS`) is never barred. Apagar de vez only for a deactivated company, confirmed by typing its name (`nomeConfere`, again in SQL), with the LGPD export offered first (`/exportar`, streamed ZIP, one CSV per table, read in batches by `LEITURA_DA_EXPORTACAO`: big tables keyset by an EXISTING `(client_id, created_at|opened_at)` index plus `id`, with a second pass for null ordering values, the rest by primary key; 2000 rows per batch, 200 for `knowledge_chunks`; `cliente.csv` is `COLUNAS_DO_CLIENTE`, the whole `clients` row, checked against the generated types). Never create an index on `chat_messages` for this (it locks writes).  (why: docs/adr/2026-10-15-two-step-company-deletion.md)
- The purge is ONE routine, `apagarCliente` (`lib/admin.ts`), in this order: catalog check (`admin_tabelas_fora_da_purga`), logins that belong to no other company (never an admin), Asaas cancel (`deleteSubscription`; failure stops), Storage files by `{client_id}/` prefix (`admin_arquivos_do_cliente`, a per-bucket range on the `name collate "C"` index; failure stops), Evolution `logoutInstance` then `deleteInstance` (`DELETE /instance/delete/{instance}`, 404 = already gone; a failure is a pending item, never a stop), `admin_apagar_cliente` (one transaction, surviving audit row), then the logins. Only existing helpers in `lib/asaas.ts` and `lib/evolution.ts`; never invent an endpoint. Every table with `client_id` is in `TABELAS_DO_CLIENTE` (`lib/admin-purga.ts`, delete order) or in `TABELAS_MANTIDAS` (kept on purpose: `billing_events`, the fiscal record; key `on delete set null`, stamped with `deleted_client_id`/`deleted_client_name` by `admin_apagar_cliente`, `p_mantidas`); a new table goes into one of them in the same delivery. The export covers both (`TABELAS_DA_EXPORTACAO`).  (why: docs/adr/2026-10-15-two-step-company-deletion.md)
- Never purge a real tenant in tests: `e2e/central-clientes-conta.serial.spec.ts` creates and purges its own disposable company; OBS is only marked, extended, deactivated and restored.  (why: docs/adr/2026-10-15-two-step-company-deletion.md)
